# Test Specification

## 1. Purpose

Define deterministic evidence required to accept MultiVideoSyncPlayer behavior.

Tests must cover pure synchronization math, state transitions, media coordination, project persistence, capture, local-only behavior, and the real Windows workflow.

Passing tests are evidence, not proof. Real-camera acceptance remains required for the core use case.

---

## 2. Test levels

### Unit

Pure logic without browser/Tauri side effects:

- global/local time mapping;
- offset derivation;
- sync state transitions;
- sync undo history;
- drift classification policy;
- project schema migration/validation helpers;
- path resolution candidate ranking;
- capture file naming.

### Component / integration

React/media-controller boundaries using test doubles where appropriate:

- right-pane state changes;
- video registration/removal;
- global seek fan-out;
- temporary unlock behavior;
- project save/load orchestration;
- error presentation.

### Tauri/Rust

- local file read/write boundary;
- atomic project write behavior;
- path handling;
- permission/write failures;
- any custom Tauri command serialization.

### Media integration

Run with generated/known MP4 files to validate real HTMLVideoElement/WebView2 behavior.

### Manual Windows acceptance

Use actual application package and real camera files.

---

## 3. Fixture strategy

Do not commit huge media files.

Use small deterministic CFR MP4 fixtures generated by a script where possible.

Recommended generated set:

- `cam-a.mp4`: common event at local 2.000 s;
- `cam-b.mp4`: same event at local 5.250 s;
- `cam-c.mp4`: same event at local 0.750 s;
- known CFR, e.g. 30 or 60 fps;
- visible frame counter/time pattern if easy to generate;
- short duration for ordinary tests.

A separate long-duration fixture or repeated playback loop may be used for drift characterization.

FFmpeg may be a **development/test fixture generator** without becoming a runtime product dependency.

Real AKASO files should remain outside Git and be used for manual acceptance.

## 4. Core synchronization tests

### SYNC-001 — offset derivation

Given aligned local times:

- A = 2.000 s
- B = 5.250 s
- C = 0.750 s

When a sync relationship is registered, mapping one global reference must reproduce all three aligned local times within the math tolerance.

### SYNC-002 — round trip

For each video:

`global -> local -> global`

must return the original value within floating-point tolerance.

### SYNC-003 — negative local time

A global time before one video's synchronized start must not produce an invalid negative seek.

Expected UI/controller behavior must be explicit and stable.

### SYNC-004 — after-end local time

A global time beyond one video's duration must not seek past the media boundary or crash.

### SYNC-005 — sync state machine

Allowed transitions include:

- NOT_SET → LOCKED after successful register;
- LOCKED → TEMPORARILY_UNLOCKED;
- TEMPORARILY_UNLOCKED → LOCKED via Restore Sync;
- TEMPORARILY_UNLOCKED → LOCKED via successful Re-sync.

Illegal/incomplete transitions must fail predictably.

### SYNC-006 — temporary movement isolation

Move video B while TEMPORARILY_UNLOCKED.

Expected:

- B runtime position changes;
- registered sync point and offsets remain byte-for-byte/logically unchanged.

### SYNC-007 — restore sync

After individual movement, Restore Sync returns all videos to positions derived from the preserved relationship and reference global time.

### SYNC-008 — re-sync save as new

Re-sync Here + Save as New creates another sync point without changing the prior point.

### SYNC-009 — re-sync replace

Re-sync Here + Replace changes only the selected sync point after confirmation.

### SYNC-010 — undo

Immediately after a sync-changing action, Undo restores the previous sync data/state.

## 5. Shared playback tests

### PLAY-001 — locked play

From LOCKED and synchronized paused positions, Play invokes all participating video controllers.

### PLAY-002 — locked pause

Pause stops all participating videos and freezes global reference.

### PLAY-003 — pre-play stale correction

Deliberately move one video away from its expected local time while preserving LOCKED test state.

Before playback begins, controller must correct material mismatch; the stale stream must not intentionally start from its old location.

### PLAY-004 — global seek

Seek global time T.

Each video receives its mapped valid local target.

### PLAY-005 — seek settle

The controller must not report global seek complete before participating media has reached a usable settled/seeked state according to implementation policy.

### PLAY-006 — frame forward

For verified CFR master/active media, Next Frame advances global time by one verified frame duration and remaps all videos.

### PLAY-007 — frame backward

Previous Frame performs the inverse without producing negative local seeks.

### PLAY-008 — unsupported frame semantics

For metadata marked unknown/VFR, exact frame-step action is disabled or clearly marked best-effort; the app must not silently use a fabricated FPS.

## 6. Drift tests

### DRIFT-001 — ignore small error

Error below configured ignore threshold produces no correction.

### DRIFT-002 — correct material error

Error above hard-correction threshold produces the configured correction behavior.

### DRIFT-003 — no continuous hard seek

Stable playback inside tolerance must not repeatedly seek slaves.

### DRIFT-004 — pause/resume

After pause then resume, slave streams converge to expected synchronized positions without a visible/stale-start race in the test harness.

### DRIFT-005 — 10-minute characterization

Using generated/real media, record max and distribution of sync error over approximately 10 minutes of playback on the reference development machine.

This is an engineering characterization. Record hardware, WebView2 version, video properties, thresholds, and observed corrections.

---

## 7. Media input tests

### MEDIA-001 — multi-select

Open at least three supported files in one native selection operation.

### MEDIA-002 — independent failure

One invalid file among valid selections reports its own error and does not discard valid files.

### MEDIA-003 — direct local file

Normal open/play does not create an application-owned full-size duplicate of the source media.

### MEDIA-004 — source unmodified

File size and modification timestamp/hash evidence before/after normal review show the application did not modify the original.

### MEDIA-005 — metadata

Supported file obtains duration/native dimensions and verified CFR timing metadata.

### MEDIA-006 — unsupported metadata

A media file whose exact frame timing cannot be verified remains playable if decoder supports it, while exact frame-step availability is represented honestly.

---

## 8. Project persistence tests

### PROJ-001 — save valid project

Save produces valid JSON with expected `schemaVersion`.

### PROJ-002 — round-trip

Serialize then deserialize a populated project and compare all required persistent domain fields.

Runtime-only objects such as HTMLVideoElement references must not appear.

### PROJ-003 — restart restore

Save project, close application, restart, open project.

Restore:

- video order;
- labels;
- sync points;
- offsets;
- active point;
- global time;
- playback speed;
- split layout;
- active/master identity if persisted.

Do not auto-play on load.

### PROJ-004 — relative path relocation

Move the project folder and its relative `videos/` subtree to another location/drive-like test root.

Expected: files resolve through relative paths without manual repair.

### PROJ-005 — absolute fallback

When relative path is unavailable but original absolute path remains valid, load succeeds.

### PROJ-006 — missing media

Missing file is reported without deleting its project synchronization metadata.

### PROJ-007 — locate file

User-assisted replacement updates the runtime source while preserving associated project video identity/sync data after validation.

### PROJ-008 — locate folder

When implemented, deterministic matching repairs multiple moved files and does not auto-match ambiguous candidates without user confirmation.

### PROJ-009 — malformed JSON

Malformed project fails with clear error and no partial destructive changes.

### PROJ-010 — unsupported future schema

A project with newer unsupported `schemaVersion` is rejected clearly rather than guessed.

### PROJ-011 — failed write preserves prior file

Inject/write to failing destination during update.

The previous valid project must remain intact.

## 9. Capture tests

### CAP-001 — current native frame dimensions

For a known 1920×1080 source, Current Video Frame output PNG is exactly 1920×1080 even when UI pane is smaller.

### CAP-002 — 4K dimensions

For a 3840×2160 fixture/real file, output is 3840×2160 if the capture path supports the decoded frame.

### CAP-003 — all video frames

With three synchronized sources, outputs exactly one file per source and all captures correspond to the same global target moment.

### CAP-004 — deterministic naming/no overwrite

Repeated capture at same timestamp must not silently overwrite an existing file unless explicitly designed. Add sequence/suffix or safe collision policy.

### CAP-005 — current split view

Composite capture matches the video-grid region, includes pane labels/global time required by the UI design, and excludes irrelevant OS chrome.

### CAP-006 — write error

Capture destination permission failure is surfaced and does not crash the app.

---

## 10. Local-only tests

### LOCAL-001 — offline startup

Disconnect external network. Installed app starts and core workflow functions.

### LOCAL-002 — no external requests

Exercise:

- startup;
- open files;
- playback;
- sync;
- project save/load;
- capture;
- shutdown.

Observe process network activity. No intentional external TCP/UDP/HTTP/WebSocket connection from the application should occur.

Internal OS/WebView2 behavior outside the application process must be distinguished from application-initiated external network behavior.

### LOCAL-003 — packaged assets

Inspect built app/runtime to verify no required fonts/scripts/images are fetched from CDN/remote URLs.

### LOCAL-004 — source scan

Search production code/config for remote runtime URLs, updater configuration, analytics SDKs, and network plugins.

Any allowed documentation-only URL must not be executable runtime behavior.

## 11. UI tests

### UI-001 — synchronization status

The right pane clearly shows one of:

- SYNC NOT SET
- SYNC LOCKED
- SYNC TEMPORARILY UNLOCKED

### UI-002 — unlocked choices

TEMPORARILY_UNLOCKED visibly offers both Restore Sync and Re-sync Here.

### UI-003 — destructive confirmation

Replacing/updating a sync point via re-sync requires explicit confirmation.

### UI-004 — active pane

User can identify/select active video for frame-step/reference behavior.

### UI-005 — 2–4 video layout

Layout remains usable for 2, 3, and 4 videos without a separate layout editor.

### UI-006 — local indicator

LOCAL/LOCAL ONLY status is visible but does not consume significant video area.

---

## 12. Error and boundary tests

Cover:

- zero videos;
- one video;
- 2–4 normal videos;
- duplicate file selection;
- empty/zero-duration or malformed media;
- one video shorter than current global range;
- seek before local start;
- seek beyond local end;
- deleted file after project save;
- read-only project directory;
- path containing spaces/non-ASCII characters;
- very long Windows path if supported by environment;
- cancelled native dialogs;
- capture with no active video;
- project save with unsynchronized state.

---

## 13. Performance tests

### PERF-001 — memory

Three 1080p videos must not be loaded entirely into application memory.

Record working set during normal playback and after seek loops.

### PERF-002 — three 1080p CFR

Core workflow should be usable with three 1080p H.264 CFR streams on the reference development machine.

Record:

- CPU;
- memory;
- GPU/video decode utilization where available;
- dropped/stalled behavior;
- drift error.

### PERF-003 — three 4K characterization

Run on available reference hardware and document result. This is not a universal pass/fail guarantee for v1 unless later promoted to a release requirement.

---

## 14. Real-camera acceptance

Use three independently started AKASO V50 Elite recordings of the same event.

Procedure:

1. open all three files;
2. independently move each to a clearly shared event;
3. Register Sync Point `Start`;
4. lock and play for several minutes;
5. pause;
6. step forward/backward;
7. global seek;
8. Temporary Unlock;
9. inspect one video independently;
10. Restore Sync;
11. Temporary Unlock again;
12. manually improve alignment;
13. Re-sync Here → Save as New;
14. capture current active native frame;
15. capture all native frames;
16. capture split view;
17. save project;
18. close app;
19. restart and load project;
20. verify equivalent synchronized state.

Record visible drift or correction artifacts.

---

## 15. Release gate

A release candidate cannot be called complete until:

- required automated unit/integration tests pass;
- TypeScript lint/type checks pass;
- Rust fmt/clippy/tests pass;
- production Tauri build succeeds;
- LOCAL tests pass;
- project round-trip/restart acceptance passes;
- native capture dimensions pass;
- real three-camera acceptance passes;
- known limitations are documented;
- `THIRD_PARTY_NOTICES.md` matches actual reused code/dependencies.
