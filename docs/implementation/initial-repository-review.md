## Validated architectural boundary

The first implementation must follow `docs/architecture/preimplementation-decisions.md`.

Key frozen boundaries:

- Windows 10/11 x64 first;
- Tauri 2 + React/TypeScript + Vite + WebView2;
- npm / Node 24 LTS;
- no production localhost server;
- Direct Local File, no mandatory import/copy;
- Tauri asset protocol for media URLs;
- narrow Rust filesystem commands rather than broad frontend filesystem permissions;
- official Tauri dialog plugin for file selection;
- `shiguredo_mp4` is the first MP4 metadata/CFR parser candidate;
- no FFmpeg runtime;
- no state-management framework;
- no updater/network/cloud/analytics dependencies;
- project format is JSON with `.mvsp` extension and `schemaVersion` from v1;
- Canvas for native frame and composite captures;
- release packaging uses WebView2 `offlineInstaller`.

## Existing contracts / invariants

The implementation must preserve these from the specification:

1. Video bytes remain in the original selected files.
2. Loaded videos are not uploaded.
3. Synchronization is explicit and based on one global time plus per-video offsets.
4. Temporary unlock does not mutate registered synchronization relationships.
5. Only explicit Register / Update / Re-sync actions may change synchronization data.
6. Project persistence stores references/state, not video contents.
7. Exact frame stepping is only promised for verified supported CFR media.
8. Runtime networking is absent except Tauri's internal IPC/local asset mechanisms.
9. Existing open-source work must be investigated/reused where appropriate before custom implementation.
10. Licensing provenance must be known before third-party source is copied.

## Required Phase 0 evidence

### Direct Local File

For at least one MP4:

- native picker returns original path;
- WebView2 plays the file;
- duration/width/height are available;
- application does not create a full-size copy of the source file;
- source file timestamp/hash/size is not modified by opening/playback.

### MP4 timing metadata

For `shiguredo_mp4` first candidate:

- identify video track;
- obtain track timescale/duration;
- obtain enough sample timing information to infer/verify CFR or classify unknown/unsupported timing;
- record parser version and license;
- demonstrate that parsing does not require reading a multi-GB file fully into memory.

If a representative AKASO file is available, use it. If it is not available in the implementation environment, the generic MP4 proof may proceed but the implementation report must mark AKASO-specific evidence as pending; do not falsely mark the full media contract verified.

### Native capture

- draw current frame at `videoWidth × videoHeight`;
- encode PNG;
- save through local Rust/file boundary;
- verify PNG dimensions equal source video dimensions.

### Drift characterization

For three CFR videos:

- synchronized start baseline;
- record media-time error over a sustained run;
- record pause/resume behavior;
- record seek/resume behavior;
- provide raw or summarized measurements sufficient to choose later drift thresholds.

If a full 10-minute automated run is impractical in CI, provide a repeatable local/manual measurement command/harness and at least a shorter deterministic development measurement. The later locked-playback PR must complete the long-run acceptance before its merge.
